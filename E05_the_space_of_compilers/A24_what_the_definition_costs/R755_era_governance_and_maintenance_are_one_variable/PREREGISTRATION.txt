ESTIMAND -- what IS identified, having established what is not
--------------------------------------------------------------------------------
Within `FORMULATION.md`'s own 99-commit history, the number of NEW `R###` citations introduced per
commit over that history: did the citation-adding rate DECLINE over its own life, or stay steady and
then stop?

That is a within-document time series with n = 99 commits, governance and document identity held
constant by construction, and it separates two mechanisms that the between-document design cannot.

--------------------------------------------------------------------------------
IDENTIFICATION
--------------------------------------------------------------------------------
IDENTIFIED and exact: git records every commit's diff, and a NEW citation is a round id appearing in

STATEMENT as the comparison stream.

NOT IDENTIFIED, and reported as such rather than attempted: whether being ungated CAUSES a flagged
rate. One treated document is n=1 on the treatment; no amount of commit-level data changes that.

--------------------------------------------------------------------------------
⛔ THE ARITHMETIC, DERIVED BEFORE MEASURING
--------------------------------------------------------------------------------
FORCED, labelled derivations, not evidence:
  - one treated document is n=1 on the treatment. No commit-level n rescues a document-level
    contrast. This is why the round changes question rather than gathering more data.
  - new citations per commit is bounded below by 0, so a declining series is bounded and its OLS
    slope is not a free parameter near the floor. A slope near zero at a floor of zero is
    UNINFORMATIVE about decline, and the terminal-cutoff shape must be read from the series, not
    from the slope alone.
  - round ids are a logical clock. Any statement of the form "the document is N rounds old" is NOT a
    statement about time, and this round does not convert between them.

STRONGEST CONFOUND, written BEFORE the run: commits differ enormously in size, so a large commit
adds more citations for reasons unrelated to intent. CONTROL IN THE SAME ITERATION: report new
citations per commit BOTH raw and per added line, and if the two disagree in sign the rate is a
property of commit size and is reported as such.

--------------------------------------------------------------------------------
KILL -- CONDITIONAL, gated on the controls
--------------------------------------------------------------------------------

else:
        UNVERIFIED. Never OVERTURNED, never CONFIRMED.

--------------------------------------------------------------------------------
CONTROLS
--------------------------------------------------------------------------------
POSITIVE   `STATEMENT.md`'s commit stream is known to be live -- it received a commit today. Its
           new-citation count must be non-zero across recent commits. BAND, COMPUTED: floor = a
           counter that never counts (0 on a stream known to add citations), ceiling = the total
           distinct citations in the file. The measured value must sit strictly between.
g=0        a commit touching the file but adding no `R###` must score 0, not be skipped. A skipped
           zero would raise the mean and hide exactly the decline under test.
NEGATIVE   shuffle the commit ORDER and refit the slope. The trend must collapse toward zero. World
           excluded: "any ordering of these commits shows this slope".
SHAM       the same operation with the INGREDIENT ABSENT, not inverted. Ingredient = being a
           CITATION. Count added occurrences of a token that is not a citation -- the `⛔` marker --
           per commit, and fit the same slope. If it declines identically, the trend is about commit
           style rather than about citing.
PLACEBO    the same commit stream counted twice -> exactly 0 difference, reported as 0 of N.
NOISE      no rng except NEGATIVE's shuffle, seeded, and swept over 5 seeds with the spread printed.
UNIT       instrument unit = a COMMIT; claim unit = the DOCUMENT's citing practice. Not equal --
           commits vary in size by orders of magnitude -- so the per-added-line normalisation is
           reported beside the raw count and the two are never merged.
