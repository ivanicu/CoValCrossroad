R678 · PRE-REGISTRATION — written before any git history is walked for this question.

THE GAP  R677 could not say how many five-member sets denote a ③-reading extension: 0 under a
         majority aggregator, 1 under any-or-earliest. The aggregator was a free parameter because
         nothing in the artifacts marks which citation COMPUTED a set and which COPIED it. Git holds
         that fact and no new convention is needed: the producer is the earliest commit whose diff
         introduces the set into a results JSON.

POINT A     5 of the 6 sets receive a UNIQUE producer commit.
INTERVAL A  [3, 6]
POINT B     under producer-based denotation, 2 sets denote a ③-reading extension.
INTERVAL B  [1, 4]
DIRECTIONAL (separately failable) the producer-based count differs from BOTH R677 aggregators
            (0 majority, 1 any/earliest) -- i.e. the lineage fact is not reproduced by either
            popularity rule.
KILL        if fewer than 3 sets receive a unique producer, git does not supply the lineage either,
            the approach dies, and R677's range 0-1 stands as the final word.
CONTROLS
  POSITIVE  a set whose producing round is KNOWN by name must resolve to that round.
  g=0       the producer finder must return NOTHING for a set that was never committed -- if it
            always returns something, it is matching rather than locating.
  NEGATIVE  a synthetic set of real arm names in a combination never committed -> no producer.
  PLACEBO   the search run twice returns the identical producer for every set.
IDENTIFICATION LIMIT, STATED FIRST
  a set introduced by MODIFYING an existing artifact is found only if modified files are scanned as
  well as added ones; both are scanned. But a set that was computed in one round and first WRITTEN
  in another is attributed to the writer, not the computer. Git records writes, not computations,
  and that gap is not closable from history alone.
