R783 · the released core's shortness is in the RELEASE, not the pipeline — and 18 cores are never scored
WRITTEN BEFORE ANY CODE FOR THIS ROUND. 2026-08-06.

--------------------------------------------------------------------------------
WHY THIS ROUND EXISTS
--------------------------------------------------------------------------------
R782 measured, from `sat_coval_core.npz`, that the released core carries 4 criteria on 925 prompts, 3
on 42 and 2 on 1, and made that its headline. §3 says an attack applies hardest when it might
succeed, and the obvious attack on my own freshest claim is: **that is the SCORING PIPELINE's count,
not the released object's.** R782's own E1b flagged the weakness — `coval_core` has NO readable
`core_*.json`, so its criteria were never read, only its sat indices counted.

CHECK #385 FOUND THE SOURCE. `data/conversation_rubrics.jsonl` carries, per conversation, a
`coval_core` list and a `coval_full` list of `{"criterion": str}` items. **986 records.** The release's
own distribution:
    coval_core   {2: 1, 3: 43, 4: 942}   -> 44 of 986 carry FEWER than four criteria
    coval_full   min 4, max 39           -> 0 below 4
So the attack FAILS and R782 is confirmed at the source: the shortness is shipped, not introduced, and
the rubric never runs out. ⚠ AND THE ID SPACES ARE DISJOINT — 0 of 968 scored prompt ids appear as
release conversation ids (NEXT_SITE.md item 2: the join was recovered from criterion TEXTS) — so this
round compares MARGINAL distributions, which is sufficient for the size question and is not a join.

⭐ AND IT SURFACES SOMETHING NEW: **986 released records against 968 scored prompts. 18 released cores
are never scored**, and nothing in this arc has ever asked which.

--------------------------------------------------------------------------------
THE ARITHMETIC, DERIVED BEFORE MEASURING
--------------------------------------------------------------------------------
D1  A MARGINAL COMPARISON OVER DIFFERENT-SIZED POPULATIONS CANNOT MATCH EXACTLY. 986 release records
    minus 968 scored prompts is 18, so any per-size difference between the two distributions is
    bounded by 18 and a residual of that size is evidence of nothing. **DERIVATION.** Only a residual
    LARGER than 18 in some cell would indicate a pipeline effect.
D2  A MULTISET IS ORDER-INVARIANT, so permuting the release's record order cannot change the size
    distribution. **The permutation negative is therefore void for this instrument and is NOT built**
    — the discipline of ledger 1125 and 1129, applied before the run rather than after.
D3  A SHAM IS UNDEFINED FOR A COUNTING INSTRUMENT. There is no ingredient to remove from "count the
    length of a list". Ledger 1131's remedy applied prospectively: **check that the object HAS the
    thing a control removes before building the control.** The cross-instrument agreement in E1 does
    the work a sham would otherwise be asked to fake.

STRONGEST CONFOUND, written BEFORE the run: the release file may contain records the benchmark never
intended to score — duplicates, or conversations withdrawn — so "18 unscored" could be a property of
the file rather than of the pipeline. CONTROL IN THE SAME ITERATION: count DISTINCT conversation ids
in the release and report duplicates explicitly; if ids repeat, the 18 is arithmetic about a file with
repeats and is stated as such.

--------------------------------------------------------------------------------
WORLDS
--------------------------------------------------------------------------------
A · THE SHORTNESS IS SHIPPED. The release's own `coval_core` distribution has entries below 4 and the
    sat file's matches it within D1's bound of 18. Then R782's headline is confirmed AT THE SOURCE and
    upgrades from "the scored core" to "the core as released", and the definition's size clause is
    contradicted by the object the definition was written from.
B · THE SHORTNESS IS THE PIPELINE. The release is uniformly 4 and the sat file is ragged. Then R782's
    headline is RETRACTED to "the scored core", and the finding becomes a provenance defect in the
    scoring artifacts rather than a fact about the definition.
C · BOTH RAGGED, DISAGREEING BEYOND THE BOUND. Some cell differs by more than 18. Then neither
    instrument can be trusted on size and the question is UNVERIFIED pending the recovered join.

PREDICTION MATRIX
  A -> release has cells below 4 AND every |release_cell - sat_cell| <= 18
  B -> release has 0 cells below 4 AND sat has > 0
  C -> some |release_cell - sat_cell| > 18

--------------------------------------------------------------------------------
KILL -- CONDITIONAL, gated on the controls
--------------------------------------------------------------------------------
if OBJECT passes (the release parses; every record carries both keys; ids counted with duplicates
   reported -- exit 2 otherwise) and POSITIVE fires (synthetic records of known size are counted
   exactly, and a deliberately broken counter does NOT pass) and g=0 fires (an empty list counts 0)
   and PLACEBO fires (recounting the same file returns identical counts):
        release below 4 AND all residuals <= 18   -> WORLD A
        release uniformly 4, sat ragged           -> WORLD B
        some residual > 18                        -> WORLD C
        otherwise                                 -> report; claim no world.
else:
        UNVERIFIED. Never OVERTURNED, never CONFIRMED.

--------------------------------------------------------------------------------
CONTROLS
--------------------------------------------------------------------------------
OBJECT       the release parses; every record has `conversation.id`, `coval_core`, `coval_full`;
             distinct id count reported beside the record count. Exit 2 otherwise.
CROSS-INSTR  the release JSON and the scored npz counted independently and compared cell by cell
             against D1's bound of 18. **This is the round's real control** — two instruments that
             share no code path, on one object.
PLACEBO      recount the same file: identical counts.
g=0          an empty criterion list counts 0, and a record with no `coval_core` key is reported, not
             silently skipped.
POSITIVE     inject synthetic records of sizes {0, 1, 4, 39} and require exact recovery; and run a
             deliberately BROKEN counter (character length instead of list length) which must NOT
             reproduce the distribution. BAND, COMPUTED: floor = the broken counter's answer, ceiling
             = the exact answer on the injected records; the criterion sits strictly between.
NEGATIVE     ⛔ NOT BUILT. D2: a multiset is order-invariant, so a record permutation cannot move the
             distribution. Building it would be the void control of ledger 1125.
SHAM         ⛔ NOT BUILT, and this is a decision rather than an omission. D3: a counting instrument
             has no ingredient to remove. Ledger 1131 applied before the fact.
DUPLICATES   distinct ids vs record count, reported, because the confound above turns on it.
UNIT         instrument unit = a JSON list length; claim unit = a released conversation's core size.
             **Equal**, and stated as two strings so the equality is a check rather than an assumption.
